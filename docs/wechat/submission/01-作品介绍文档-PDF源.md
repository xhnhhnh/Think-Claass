## 1. 作品概述

### 1.1 一句话

**Think-Class** 是一个课堂教学与班级激励平台：老师在电脑端管理班级、发布作业、掌握全班薄弱点；
学生在微信小程序里查看成长、作答作业、练 AI 智学、用班级积分兑换奖励。

### 1.2 它长什么样

小程序（原生微信小程序 + TypeScript，共 11 个页面）：

| 角色 | tab | 做什么 |
| --- | --- | --- |
| 学生 | 成长总览 / 我的作业 / 积分商城 / 我的 | 看积分与等级、领奖状、作答作业、查看批改结果、练智学练单、兑换奖励 |
| 教师 | 班级 / 作业 / 智学看板 / 我的 | 看班级与名单、发布作业、看全班集体薄弱知识点、一键派发练习单 |
| 家长 | 与学生同 tab | 查看孩子的表现（`user.studentId` 为空时隐藏学生专属区块） |

电脑端（React 18）承担教师与超管的重操作：题目与试卷编辑、AI 出题、班级功能控制台、
大屏展示、数据分析与后台管理。

### 1.3 为什么是"小程序的形态"

课堂的真实约束是**时间碎片化**：老师要在一节课的间隙里公布积分、发作业；学生要在课间十分钟里
知道"我今天该练什么"。这些动作必须发生在手机上、在微信里、在两三下点击之内完成 —— 而不是
打开电脑、登录一个网站。所以本项目把**学生的全部日常**和**教师的高频轻操作**放进小程序，
把低频重编辑留在电脑端。

## 2. 应用场景与目标用户

### 2.1 目标用户

| 用户 | 场景 | 他的痛点 |
| --- | --- | --- |
| 中小学一线教师 | 课堂激励、作业收发、找薄弱点 | 现有积分表/小红花靠纸笔或表格，统计要手工算；想让全班练同一类错题，得自己翻卷子找 |
| 学生（小学高年级至初中） | 课间、回家后 | 不知道"我今天该练什么"；错题订正完就丢了，下次还错 |
| 家长 | 想了解孩子表现 | 只能等老师发消息，看不到连续的记录 |

### 2.2 典型使用场景（演示脚本按此顺序）

1. **课前一分钟**：老师在小程序里给全班答对的同学加积分 → 学生端"成长总览"实时变化。
2. **课间十分钟**：学生打开"我的作业"，看到一份含选择题与简答题的作业，作答并提交。
3. **一道题错之后**：学生打开"AI 智学"，拿到一份**带理由**的练习单（"你上周这道题错过 2 次，
   而且它属于你还没掌握的知识点"），直接在页面上作答，掌握度回写到错题本。
4. **老师看全班**：教师端"智学看板"列出本班集体薄弱的知识点，勾选几名学生一键派单 ——
   每人一份，题目不同。
5. **兑换奖励**：学生用班级积分在"积分商城"兑换班级内的奖励（**班内虚拟积分，不涉及任何支付**）。

### 2.3 隐私与合规姿态（写进材料，评委会核对）

- 学生由**教师/学校在知情前提下录入并管理**，学生端不提供未成年人自主注册路径。
- 学生姓名在服务端**加密存储**（`ENCRYPTION_KEY`，AES-256-CBC），且源码中**没有默认密钥**：
  密钥缺失时加解密直接失败，而不是退回一个公开的默认值。
- 不采集手机号、位置、通讯录；唯一与账号相关的外部标识是微信登录的 OpenID。
- 班内积分**不是货币**：没有充值、没有下单、没有真实交易入口。

## 3. 解决的实际问题

| 真实痛点 | 本作品的处理 |
| --- | --- |
| 激励靠纸笔，统计耗时 | 积分、奖状、排行榜、宠物成长全部自动结算；老师只做"加分"这一个动作 |
| 错题订正完就丢 | 每次作答写回错题本与知识节点掌握度，下次生成练习单时**优先这些题** |
| "今天该练什么"没人回答 | 规则引擎算出当天该练的 5 道题，**每题都给出被选中的理由** |
| 老师想知道全班弱在哪 | 智学看板按知识点汇总集体薄弱项，不需要老师自己统计 |
| 功能和课堂节奏打架 | 20 个班级功能位可在课堂主界面一键开关，学生端 tab 与入口随之实时显隐 |

## 4. 技术开发方案

### 4.1 架构：内核 + 插件

后端不是一坨路由，而是一个**最小内核 + 23 个业务插件**：

```text
packages/kernel/          存储与迁移、设置、审计、HTTP 外壳、鉴权原语 —— 零业务知识
packages/plugin-runtime/  扫描 plugin.json、校验声明、按依赖排序启动插件
packages/plugin-sdk/      插件编译所依赖的 API（ctx.db / ctx.audit / ctx.use / ctx.provide）
packages/contracts/       纯类型，跨插件边界共享
plugins/<slug>/           一个业务域：manifest + 控制器 + 服务/仓储 + 迁移 + 它发布的端口
api/                      组合根：server.ts / app.ts / app.module.ts / db.ts
miniprogram/              小程序客户端（原生 + TypeScript，无 npm 运行时依赖）
src/                      电脑端前端（features/<domain>/ 按域组织）
```

**这套架构不是画出来的，是被守卫住的。** 仓库里 20 条 guardrail（G1–G21）在 CI 里跑，
违反即失败：内核不得出现任何业务表名或功能键（G5）、插件之间只能通过 `ctx.provide` /
`ctx.use` 通信（G1）、`packages/contracts` 只能是类型（G6）、表结构只能出现在迁移里（G17）、
HTTP 接口面被快照冻结、`ENCRYPTION_KEY` 源码中不得有默认值（G18）。

### 4.2 技术栈

| 层 | 选型 |
| --- | --- |
| 小程序 | 原生微信小程序 + TypeScript（`wx.*` 类型手写维护，零 npm 运行时依赖）；自定义 `tabBar` 按角色与班级功能位动态渲染 |
| 前端 | React 18 · TypeScript · Vite 6 · Tailwind CSS 3 · TanStack Query 5 · Zustand |
| 后端 | Node.js ≥ 24 · NestJS 11 + Express 4 · TypeScript（`tsx` 直跑）· 自研内核与插件运行时 |
| 数据 | SQLite（`better-sqlite3`）· 前向且带校验和的迁移 · 学生姓名静态加密 |
| 部署 | 微信云托管（容器，`deploy/Dockerfile`，单副本 + CFS 持久化）或自有服务器（PM2 + Nginx）；GitHub Actions 发布流水线 |

### 4.3 小程序端的两个关键设计

1. **双传输通道，同一套失败语义**：部署坐标集中在 `miniprogram/config/index.ts`。
   `TRANSPORT = 'request'` 走 `wx.request`（需要已备案的 HTTPS 域名白名单）；
   `TRANSPORT = 'container'` 走 `wx.cloud.callContainer`（微信云托管，**无需域名与证书**）。
   两条通道共用同一份信封判定、401 处理与错误提示，切换不改变化失败行为。
2. **会话与 401 静默续期**：任意带鉴权请求返回 401 时，客户端自动重跑
   `wx.login → /api/wechat/login`，拿到新 token 后**原请求自动重试一次**，全程无 UI；
   并发的多个 401 共用同一次续期。只有续期本身失败才清空会话回登录页。

### 4.4 工程质量（可查验，不是形容词）

| 项 | 数值 |
| --- | --- |
| 源码规模 | 879 个源文件 / 约 12.9 万行 |
| 业务插件 | 23 个（admin · ai-study · assignments · battles · challenge · classroom · collaboration · dungeon · economy · engagement · gacha · homework · identity · insights · learning · marketplace · parent-buff · payment · pet · portal · slg · system · wechat） |
| 测试 | 177 个测试文件，分四层：前端（jsdom + MSW）· 后端（真实内核与插件）· 守卫（架构棘轮）· **端到端（真实 HTTP，逐端点逐角色）** |
| 端到端 | 97 个用例：匿名不得成功、任何角色不得 500、前端真正调用的路径不得 5xx |
| 小程序端 | 26 个逻辑测试（信封 / 401 静默重登 / 动态 tab 门控 / 绑定 role），类型检查零错误 |
| CI | GitHub Actions：`npm run check` → `api:surface:check` → `guard` → `npm test`，全绿才允许发版 |

**为什么端到端那一层值得单独讲**：前端测试跑在"MSW 对一切返回 200"的假服务端上，后端测试每个套件
只碰少数几个路由 —— 两者都绿的时候，客户端和服务端完全可能对不上。这一层就是为这个盲区存在的，
它上线后第一次运行就抓到过一个真实缺陷（部署实例里学生调宠物接口全部 403，而 1128 个测试全绿）。

## 5. 小程序创新点

> 竞赛评审的"产品创新性"占 **30 分**，其中明确列了"AI 应用创新"。这一节请**保留具体机制**，
> 不要压缩成"我们使用了 AI"。

### 5.1 创新点一：可解释、可复现、模型不可越界的智学引擎

**问题**：市面上的"AI 推荐题目"几乎都是把题库丢给大模型，让它挑。结果是同一份错题今天推这五道、
明天推那五道，学生无法续做、老师无法复核，而且模型可以凭空塞进一道没人验证过的题。

**本作品的做法**：把"选哪些题"和"怎么表述"拆开，并且**只把后者交给模型**。

- **选择权在规则引擎**：五个整数权重的确定性函数 —— 掌握度缺口、重复出错次数、薄弱知识节点、
  难度匹配、新鲜度 —— 同样的输入永远得到同一份题单，同一份题单可以被复现和复核。
- **模型只允许做两件事**：重排这份候选的顺序、改写"为什么选它"的理由。
  模型输出的题目 id 若不在候选列表里，**直接丢弃**，绝不映射到别的题上。
- **没有模型也完整可用**：规则引擎独立成立（默认部署就是这个形态），
  所以这不是"降级版"，而是"模型可选、规则兜底"。
- **界面必须说实话**：每道题的来源（规则 / 模型）在 UI 上有标记，
  理由是模板句还是模型改写句，看得见。

**一句话**：这是"AI 不能凭空造题"的个性化练习引擎 —— 与"给大模型套一层壳"相比，
它解决的是教育场景里真正要命的东西：**可解释、可复现、可追责**。

### 5.2 创新点二：AI 判分只判它配判的

- 客观题由确定性函数判分，不经过模型（更快、更省、永远一致）。
- 主观题/简答题**只有在有参考答案时**才交给模型；模型不可用时返回"这道题需要老师"，
  `score` 明确为 `null`。
- 模型不可用**不会让请求失败**：老师按下「AI 判分」后，客观题的成绩照常保存，
  界面上一行字说明模型为什么没参与 —— 而不是一个 503 加一片空白。

### 5.3 创新点三：把"班级功能开关"做成课程节奏的一部分

20 个班级功能位（积分商城、宠物、抽奖、团队任务、跨班大乱斗、领土扩张……）对**新班级默认全关**，
教师按课堂进度打开。学生端的小程序 tab、页面入口与守卫组件全部由这套开关驱动，
并遵循一条刻意的原则：**开关状态无法确认时，受控入口一律隐藏**（让学生点到一个必然 403 的入口，
比少显示一个入口糟糕得多）。

### 5.4 创新点四：一张表跑四个端，且边界由机器守住

同一套鉴权、同一份班级功能开关、同一份领域数据，服务教师端、学生端、家长端与超管端（网页 + 小程序）。
跨域访问只能走插件发布的端口，内核不得知道任何业务词汇 —— 这些约束由 CI 里的守卫强制执行，
而不是靠开发者自觉。
