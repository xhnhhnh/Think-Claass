# 启动提示词 · 复制粘贴到全新对话即可

> **设计原则：这份提示词只写「不变的东西」，绝不写「状态」。**
>
> 上一版把它写成了「P4.3b 未开始、端点必须是 288、棘轮是 62/70/76」——
> 结果另一个对话在同一工作区把 P4.3b 和 P5 大半做完了，这份提示词当场变成误导。
> 状态会变，规则不会。**状态一律由 `HANDOFF.md` 承载，它是每轮都在更新的那个文件。**

---

```
【任务】ThinkClass「最小 Core 内核 + 无限 Plugins」架构重构（长期目标）

请先调用 create_goal 创建一个长期目标，然后自动持续执行、每轮交付一个可验证的
完整片段，直到全部阶段完成，中途不要停下来问我是否继续。

目标一句话：把现有前端、后端、数据库与整体架构重构为真正的
Core → Plugin Runtime → Plugin API/SDK → Plugins。

────────────────────────────────────────
【第一步：读文档，别先动手】
  D:\think-class\docs\migration\HANDOFF.md    ← 唯一权威入口，先完整读它
  它是逐轮更新的，里面有：当前状态、阶段进度、已建成架构、护栏与棘轮、
  下一步目标、已知遗留与坑、以及最重要的「第一条规矩」。
  同目录 00-baseline.md … 04-*.md 是各阶段详细记录。

  ⚠️ 「下一步目标」在 HANDOFF.md 的 §1.1。它写的是**判据**（验收命令、硬性数字、
     必须先做的裁决、明确不在范围内的事），不是进度叙述 —— 上一版把下一步写成散文，
     两轮就过期了。先读 §1.1 再动手。§1 是状态、§1.1 是目标；
     两者与工作区冲突时，一律以工作区为准。

【第二步：核对真实状态（必须，不许跳过）】
  cd D:\think-class
  git log --oneline -3
  git status --short
  npm test
用输出核对 HANDOFF.md 里描述的状态。
⚠️ 工作区是事实，文档只是叙述；两者冲突时以事实为准，并顺手把文档改对。
⚠️ git status 不干净 = 上一轮被中断在半途。先判断那是「已完成但未提交」
   还是「改坏了」，再决定继续还是回退 —— 不要按"它应该做到哪一步"往下做。

【每轮硬性要求】
  提交前四条必须全过：
    npm run check
    npm test
    npm run api:surface -- --check     ← 端点数不得非预期漂移
    npm run guard
  完成后提交，提交信息写清「为什么」，尤其是与直觉相反的设计约束。

【环境约束】
  · 网络完全不可用（npm registry / github 均 TLS 失败）
    → 不能加任何依赖，不能 pnpm install，只能用现有 node_modules
  · 测试直接跑即可（文件策略是 full-access）

【工作方式】
  · 每轮一个可验证的完整片段，不要一次性大改
  · 测试失败或类型检查报错时，优先怀疑是真 bug，不要改测试来迁就
  · 棘轮只能降不能升：修好一处就把 allowances.json 调低
  · **迁移期间不要"顺手修"看起来明显的 bug**：它不会让任何测试变红，只会让线上
    多出没人要求的行为变化。HANDOFF §9 的 P4.3b.10 记了三个状态码被这样改掉的实例
    （探针抓回来的）。发现既有缺陷就**记录**它，把修法写进 `_known_debt`
  · 发现文档与事实不符 → 以事实为准执行，并把文档改对
```

---

## 使用说明

1. **整段代码块**复制粘进新对话的第一条消息。
2. 它没有自动创建目标时，补一句「请调用 create_goal 创建长期目标再开始」。
3. 它没跑那三条核对命令就开始改代码时，把这段再发一次。
4. **想知道"现在做到哪了"，不要问我，也不要问这份文件 —— 去看 `HANDOFF.md`。**
   这份文件只保证一件事：无论进度到哪，它都不会过期。
